# Decision Log (ADRs)

Each decision below was made deliberately during design or build. Format: **Context → Decision → Consequences / rejected alternatives**. New decisions append here as `ADR-NN`; a decision that grows large or gets superseded graduates to its own `NNNN-title.md` file.

Status legend: ✅ accepted · 🔁 superseded · 🧪 provisional

---

## ADR-01 — RAG, not fine-tuning ✅
**Context.** We want the reviewer to learn from accumulated review knowledge.
**Decision.** Knowledge is a curated, provenance-backed, *editable* corpus retrieved at review time — never baked into model weights.
**Consequences.** Inspectable, deletable, instantly updatable, local-first; no GPU/training loop. *Rejected:* fine-tuning — opaque, stale-fast, can't audit or surgically edit a single lesson.

## ADR-02 — Model-agnostic MCP server; two LLM contexts ✅
**Context.** Reviews must be unbiased and ride the user's existing agent subscription.
**Decision.** The reviewer is an MCP server. *Interactive review* uses whatever agent connects (fresh session = unbiased). *Offline batch* work (if any) makes its own API calls.
**Consequences.** No vendor lock-in; the server never needs an interactive-LLM key. The fresh process is the anti-bias mechanism.

## ADR-03 — Three finding sources, one ranked stream ✅
**Context.** Pattern-matching alone is a glorified linter; raw LLM alone is biased/inconsistent.
**Decision.** Merge **first-principles** (agent reasoning, the spine), **knowledge-grounded** (retrieved pitfalls), and **deterministic** (Semgrep/ast-grep) into a single stream.
**Consequences.** Catches novel *and* recurring issues; cross-source agreement becomes a confidence signal.

## ADR-04 — Severity and confidence are independent axes ✅
**Context.** "Potential bug" is a real category users care about.
**Decision.** `severity ∈ {bug, improvement, nit}` and `confidence ∈ [0,1]` are separate. A "potential bug" = `bug` + low confidence. Ranking: `signal = severity × confidence × deviation × blastRadius − waiver`. **M12 (ADR-31)** adds a 4th value `awareness` — a different *intent* ("worth confirming", not "fix this"), triaged into its own bucket.
**Consequences.** The reviewer states honest confidence instead of faking certainty.

## ADR-05 — Prevalence interpreted by severity ✅
**Context.** A pattern in 200 places shouldn't be nagged per-line — but a *bug* in 200 places is worse, not safer.
**Decision.** Common **style** → convention (demote). Common **bug** → systemic (escalate as a migration, with blast radius). Suppression never silences widespread real bugs.

## ADR-06 — Layered code understanding, unioned by provenance ✅
**Context.** Precise call-graph resolution is language-specific and expensive; blast radius only needs *coupling*.
**Decision.** Agnostic spine (git co-change + imports + embeddings) always on; precise edges (TS compiler) as optional enrichment. All edges carry `provenance` + `weight` and are unioned.
**Consequences.** Co-change catches runtime couplings (DI/injected services) that imports and static analysis miss; no single source is trusted alone.
**Refinement (hub-damping — fixes barrel flood).** Co-change is commit-size-weighted (a 200-file format sweep contributes ≈0). Import/ref edges had no such damping, so a changed **barrel/registry** (`db/entities.ts`, `app.module.ts`, a shared `index.ts`) — imported by hundreds — painted *all* its importers as blast radius, saturating at score 1.0 (observed live: a chat-feature review surfaced unrelated **auth** files at 1.0 because they import the same changed registries). Fix: structural edges are now down-weighted by the **degree** of the changed node they radiate from — full weight at/below a hub threshold (default 20), then a `threshold/degree` falloff (`hubWeight`, `neighborhood/compute.ts`). The structural analogue of the 1/(commit-size) rule; degree is read for free from the existing frontier query. Genuine low-degree couplings now rank above registry noise. *(Superseded: the `hubWeight`/`threshold/degree` falloff was later replaced by the degree-normalized personalized-PageRank walk — the hub fix is intrinsic to the walk now, no separate knob; see `docs/design/tuning.md` §4.)*

## ADR-07 — Storage = Kùzu (durable) + FalkorDB (ephemeral); N+1 topology ✅
**Context.** Local-first, possibly many repos; want live graph debugging.
**Decision.** Kùzu (embedded, MIT, disk-backed) holds N per-repo code graphs + 1 global knowledge graph, joined at `Finding`s. FalkorDB (in-memory, multi-graph) holds ephemeral per-PR `pr_<id>` neighborhoods.
**Consequences.** Durable graph scales past RAM; ephemeral graph is cheap and inspectable in FalkorDB Browser. *Rejected:* memory-first for everything (RAM-bound at scale); Neo4j (JVM weight, GPLv3). ~~FalkorDB optional — degrades to in-process.~~ **Amended by ADR-22 (M6):** FalkorDB is now a *required* working-memory store for the review flow (AOF-persisted), no longer optional.

## ADR-08 — Knowledge graph schema ✅
**Decision.** `Category → Pitfall{trigger, why, confidence, tier} → Mitigation`; `Pitfall ─EVIDENCED_BY→ Incident` (provenance); `Pitfall ─PROMOTED_TO→ Rule`; `Finding ─INSTANCE_OF→ Pitfall` + `─AT→ CodeLocation`; `Waiver ─SUPPRESSES→ Pitfall` (scoped).
**Consequences.** Makes the `signal` formula computable and every pitfall auditable.

## ADR-09 — Markdown ⇄ graph duality ⛔ superseded by ADR-37
**Decision (original).** `plex.md` is both input (cold-start seed, overrides) and output (proposed promotions). Graph = learned engine; markdown = human steering wheel. Codifiable + high-confidence → Semgrep/ast-grep.
**Consequences.** Trust (humans read/edit a file, not a black box) + cold-start path.
**Superseded (ADR-37):** `plex.md`, markdown seeding, AND the whole promotion surface (both the markdown half and the unwired graph → ast-grep rule stubs) were removed; knowledge is learned only. A structured, committed steering surface (`plex.json`) is the planned replacement (backlog).

## ADR-10 — Feedback loop: scoped verdicts + self-discovery ✅
**Decision.** Verdicts (accept/reject/waive) carry a **scope** (`line|file|pattern-repo|category-repo|category-global`) and reweight the graph. Confirmed novel bugs become `Incident`s → may distill into `Pitfall`s.
**Consequences.** The system learns from its own discoveries, not just analyzed history.

## ADR-11 — Review-history analysis is outcome-weighted, provenance-mandatory ✅ (built, M4)
**Decision.** Source unit = `(code-before → review comment → outcome)`. Cluster across PRs; a cluster (not a singleton) distills into a pitfall; every substantive comment becomes an `Incident` and pitfalls keep their `incidentIds`. Outcome is pragmatic (merged PR ⇒ accepted/shipped); incremental per-repo cursor skips already-scanned PRs.

## ADR-12 — Language: TypeScript/Node ✅
**Decision.** Implement everything in TS/Node. Matches expertise (fastest), single runtime to ship, native TS compiler access. Python reserved only for heavy analysis clustering if ever needed.

## ADR-13 — Embeddings: pluggable provider; real-or-nothing ✅
**Context.** Opus/Claude are *not* embedding models. Embeddings power knowledge retrieval AND analysis clustering.
**Decision.** Abstract embeddings to `text → vector`. Providers: Voyage `voyage-code-3` (code-specialized, Anthropic-recommended), OpenAI `text-embedding-3-small`, Google `gemini-embedding-001`, local Ollama `nomic-embed-text`. **No fake/heuristic embeddings in real operation** — the default is `none`; the deterministic `fake` embedder is test-only. Retrieval degrades gracefully without a provider (returns nothing); analysis write paths error.
**Consequences.** Knowledge features require an explicit real provider (no silent noise — fake embeddings don't discriminate, so they pollute retrieval). Switching providers requires re-embedding (vectors aren't cross-comparable). Updated after observing fake embeddings retrieve every pitfall for any query. **M6 (ADR-22/23):** the PR brain's change attribution is embedding-based (semantic, no line/title heuristic), so embeddings are **required** for the review brain — when FalkorDB is enabled the review errors without a provider, exactly as the knowledge write paths do. (The deterministic `fake` embedder remains test-only.)

## ADR-14 — All inputs normalize to "diff vs base ref" ✅
**Decision.** Local (working/staged/branch) and GitHub PR (`gh pr diff`) inputs both reduce to one `NormalizedDiff`. PR-vs-local is not a meaningful internal distinction; `gh` is just an adapter.

## ADR-15 — v1 TS plugin uses the TypeScript compiler API, not tree-sitter ✅
**Context.** The plan named tree-sitter for the structural layer. For a TS/JS-first v1, the TS compiler API is more accurate (real symbol/import/reference resolution), needs no native build, and serves *both* structural (M1) and precise (M2) edges.
**Decision.** v1 language plugin = TS compiler API. The agnostic co-change spine stays parser-free (pure git). tree-sitter remains the documented extension path for *other* languages behind the same extractor interface.
**Consequences.** Lower dependency risk, better TS accuracy; multi-language breadth deferred to when non-TS plugins are added.

## ADR-16 — FalkorDB publishing runs in an isolated child process 🔁 (retired by ADR-30)
**Context.** The Kùzu native addon and the FalkorDB/node-redis stack **SIGSEGV when used in the same process** (verified: exit 139 even after closing Kùzu first — loading the addon poisons the process). The MCP server needs Kùzu always and FalkorDB optionally.
**Decision.** Publish neighborhoods to FalkorDB from a separate child process (`packages/neighborhood/src/falkor-worker.mjs`, plain JS, no Kùzu). The parent spawns it, pipes the job over stdin, reads a JSON result, and treats any failure as "not published."
**Consequences.** The optional viz layer can never crash the server; FalkorDB stays decoupled. Keep `falkor-worker.mjs` out of the typecheck/test globs (it's plain JS) and copy it alongside built output when packaging.

## ADR-17 — Kùzu-heavy tests run via tsx, one process per scenario ✅
**Context.** The Kùzu addon does not survive **tsx**'s runtime loader after ~5 cumulative `Database` opens in one process (SIGSEGV), and it also crashes **vitest** worker teardown (ERR_IPC_CHANNEL_CLOSED) — though tests themselves pass. Under plain `node`, 12+ open/close cycles are stable; the product (built to JS, run under node) is unaffected.
**Decision.** vitest holds **pure unit tests only**. DB-/subprocess-heavy scenarios live in `packages/engine/integration.mts` and run via `pnpm test:integration`, which invokes tsx **once per scenario** (≤2 opens each, well under the limit). `pnpm test` runs both.
**Consequences.** Deterministic green suite. Must-remember: do not pile multiple Kùzu-opening operations into one long-lived tsx process; in production reuse a Database per dir and run built JS under node.
**M6 addendum.** A process that has loaded the Kùzu addon **and** spawns the FalkorDB worker (ADR-16) SIGSEGVs on teardown **under tsx** — i.e. the PR-brain review flow (Kùzu blast radius + FalkorDB brain) cannot run in the tsx integration runner. It is stable under plain **node** (verified end-to-end). So the brain's E2E check drives the *built CLI* under node — `scripts/brain-check.mjs` / `pnpm test:brain` (skips if FalkorDB is down) — while the pure `classifyChanges` decision is covered by a vitest unit test. The long-lived MCP server (node, never exits) is unaffected.

## ADR-18 — Knowledge base is a JSON-backed embedded store (for now) ✅
**Context.** ADR-07 placed the knowledge graph in Kùzu, but the knowledge corpus is small, retrieval is embedding-based (not multi-hop graph traversal), and adding a second Kùzu DB to the hot path compounds the tsx open-limit (ADR-17).
**Decision.** Store pitfalls + incidents as append-only JSONL under `knowledgeDir` (global, `~/.plex/knowledge` by default), with embeddings stored on each pitfall and cosine retrieval in-process. The `Pitfall`/`Incident`/`Category` schema (ADR-08) is preserved as record shapes.
**Consequences.** Simple, fast, no native-DB coupling in the retrieval path; matches the plan's "let the graph earn its place." Graduate the knowledge side to Kùzu only if/when genuine multi-hop graph queries are needed.

## ADR-19 — Ship bundled JS run under node ✅
**Context.** tsx is unstable with the Kùzu addon (ADR-17); node is stable. The codebase uses extensionless (Bundler) imports node can't resolve directly.
**Decision.** `tsup` bundles the CLI and MCP server (workspace source bundled; native/heavy third-party deps external) to ESM in `dist/`, run via `pnpm start` / `pnpm start:mcp` under node. The FalkorDB child worker is copied beside the output; the external runtime deps are declared in the **root** package.json so they resolve from the root `node_modules`.
**Consequences.** Stable production runtime; dev still uses tsx for fast iteration (with the open-limit caveat). Source-of-truth for "how to ship."

## ADR-20 — Analysis distillation is agent-driven over MCP ✅
**Context.** Distillation needs generative reasoning. Doing it with a hardcoded API key (ADR-02 "offline batch") doesn't ride the user's Claude/Codex subscription, which is the whole cost motivation.
**Decision.** Split analysis: the MCP server does the mechanical scan (`analyze_scan` — fetch new PRs, denoise, record incidents, cluster) and returns clusters; the **connected agent distills them with its own reasoning** and stores results via `add_pitfalls`. The standalone path (`plex analyze` / `analyze_history`) also distills with an LLM — **by default the local `claude` CLI** (subscription, no key), or `anthropic`/`openai` via key. **There is no heuristic distiller** — a keyword heuristic can't judge whether a cluster is a real, generalizable lesson, so the LLM decides (it can SKIP a cluster). If no LLM is available, analysis **errors** rather than storing low-quality pitfalls.
**Consequences.** Distillation is always intelligent; analysis rides the subscription, mirroring the review loop. On-demand, not background — fine because the incremental cursor makes repeat runs cheap. Fits the user's PR-skill ecosystem (the **responder** skill's resolving diffs are the ideal future outcome signal).

## ADR-21 — Knowledge has scope: global vs repo ✅
**Context.** Analysis (and the agent) surface lessons that are specific to one project. Discarding them loses value *for that project*; storing them globally pollutes others.
**Decision.** Each `Pitfall` carries a `scope`: `global` (applies everywhere) or `repo` (stored, but only retrieved when reviewing its origin `repo`). Undefined = global (back-compat). The LLM classifies scope during distillation; analyzed/agent pitfalls default to `repo`. Retrieval filters: `scope === global || pitfall.repo === currentRepo`.
**Consequences.** Project-specific knowledge helps within its project without leaking elsewhere; global best-practices apply everywhere. The reviewer accumulates both kinds.

## ADR-22 — FalkorDB is the per-PR working memory, and is REQUIRED 🔁 (superseded by ADR-30: brain moved to embedded Kùzu, M11)
**Context.** ADR-07 scoped FalkorDB to an *ephemeral visual mirror* of the structural blast radius. In practice the blast radius is computed entirely from **Kùzu + the diff**; FalkorDB only received a copy to look at — a graph you only look at "produces nothing." Maintaining a second in-process code path purely so FalkorDB stays optional is an unnecessary optimization; the durable, queryable *history* of what happened on a PR is the real value.
**Decision.** Promote the per-PR FalkorDB graph from *optional viz mirror* to a **required component** of the review flow — the persistent "brain of the PR." Beyond the blast radius it holds `Round`, `Finding`, `Verdict`, and `Comment` nodes with their edges, and the orchestrator **reads and writes** it to derive round-aware signals (§ADR-23). The in-process fallback is **dropped**: if FalkorDB is unreachable, the review errors with a clear "run `pnpm db:up`" message rather than silently degrading. **FalkorDB persistence (AOF) is enabled** so the brain survives container restarts — that is what makes "history written down" real (Redis/Falkor is in-memory by default; without AOF a restart wipes it).
- **Sources of truth:** waivers stay in `<repo>/.plex/verdicts.json` (they apply across targets, independent of any one PR graph) and are *projected* into the brain; the PR brain (rounds/findings/comments) lives in FalkorDB (AOF-persisted).
- **Isolation unchanged (ADR-16):** the Kùzu addon and FalkorDB still cannot share a process, so *all* FalkorDB access — now reads as well as writes — goes through the isolated child worker, which becomes a small request/response RPC (`publish` | `query`).
**Consequences.** FalkorDB earns its place via cross-round / cross-blast-radius traversal queries that are awkward in flat JSON, and the PR history is inspectable live. Cost: FalkorDB (`pnpm db:up`) is now a hard prerequisite for reviewing, and the worker grows a read path. **Supersedes ADR-07's "FalkorDB optional / degrades to in-process" clause** for the review flow (Kùzu remains the durable code-graph store; the knowledge store remains JSON per ADR-18).

## ADR-23 — Round-aware review; "changed-without-feedback" ✅ (built, M6)
**Context.** Each review today is stateless across rounds. But a multi-round PR carries signal in the *deltas*: a change made in response to a review comment is low-risk; a change nobody asked for — slipped in between rounds — is exactly what a tiring human reviewer misses.
**Decision.** A review **target has rounds**: a round = a review invocation at a distinct head SHA, persisted in the brain (ADR-22). On a new round the orchestrator diffs round *N* vs *N−1* and classifies each changed region by **embedding similarity** (NOT line proximity — no heuristic; ADR-13): **feedback-driven** if its content is semantically close to a prior finding or PR-thread comment, else **unexplained** (changed with nothing driving it) — surfacing the *unexplained* set as a high-priority note to the fresh reviewer ("these moved with nothing explaining why — scrutinize"). PR-thread comments are ingested per round (reusing the analysis fetcher) as **facts**. Implemented: `engine/brain.ts` (rounds), `findings/rounds.ts` (the pure `classifyChanges` cosine decision), `ingest` head-SHA + inter-round-diff helpers.
**Consequences.** Multi-round reviews get sharper without re-biasing — this stays squarely inside ADR-02: only **facts** cross rounds (verdicts, comments, what changed), never the prior run's chain-of-thought. Requires head SHAs (available for PR/branch; working-tree falls back to `HEAD`). Brand-new files added by a PR have no graph node until re-index — that blind spot is unchanged and explicitly noted to the agent.

## ADR-24 — Review audit log for attribution & self-improvement ✅ (built, M6)
**Context.** We can't improve what we don't measure. Today a review leaves only `verdicts.json`; the *context that produced* each finding — which blast-radius files were in view, which pitfalls were retrieved, whether change-context was present — evaporates. We also can't answer "did the graph/knowledge actually help?" (the very question that came up confirming the analytics finding).
**Decision.** Emit an **append-only JSONL audit log** of the review lifecycle to `<repo>/.plex/log/events.jsonl`, one event per step, each tagged with a correlation key `{repo, target, round, ts}`:
- `context_assembled` — diff summary, blast-radius node ids + scores + provenance, retrieved pitfall ids + scores, `changeContext` presence;
- `findings_submitted` — per finding: source, severity, confidence, computed signal, location, triage;
- `outcome_recorded` — verdict kind + scope.
The flat log is greppable and graph-independent; the FalkorDB brain (ADR-22) is its *queryable projection*.
**Limitation (honest scope).** The server logs what it **provided** and what the agent **submitted** — not the agent's private reasoning. Attribution is therefore *correlational* ("finding X was submitted with pitfalls A,B and coupled files C,D in context"), which is enough to tune retrieval/weights, debug context assembly, and answer "what did the reviewer see." It deliberately does **not** capture chain-of-thought (ADR-02).
**Consequences.** Real-outcome tuning of retrieval and `signal` weights becomes possible; "why did this surface?" is answerable after the fact; provenance, not opinion, is what's stored.

## ADR-25 — Incremental indexing + graph staleness ✅ (built, M7)
**Context.** The full code-graph build re-parses *every* file with the TS compiler — the dominant cost, and real on large monorepos (playright). After a pull/merge the graph drifts: edges for edited files go stale and **brand-new files have no node at all** until a manual reindex, silently shrinking the blast radius. The graph already stamps `headSha` at index time (`build.ts`), but nothing reads it back. Crucially, the full graph is *worth* building once — PR-level work only **reads** it, and blast radius is meaningless without the whole repo's couplings (you expand *into* files the diff didn't touch). So the answer is "build once, refresh cheaply," not "index per-PR."
**Decision.** Three parts:
- **Staleness signal + auto-refresh.** On review, compare the graph's stored `headSha` to current `HEAD`. If it has drifted (`behind > 0`), **auto-refresh the graph incrementally before computing the blast radius** so the neighborhood is never silently stale (opt out with `autoIndex:false`); the review notes it did so (`↻`). An unknown/missing index (`behind = -1`) is only *reported*, not auto-refreshed — refreshing it would mean a surprise full rebuild mid-review.
- **Incremental indexing.** Given files changed since the stored `headSha` (`git diff --name-status <sha> HEAD`): re-extract only **added/modified** files and drop **deleted** ones — *preserving incoming edges of modified files* (delete only their Symbols + outgoing Imports/Refs, keep the File node) — then re-stamp `headSha`. Refresh becomes O(changed files). Full rebuild stays available (`--fresh`). **Co-change is recomputed fully** (not incrementally merged) in v1: its recency-decayed weights are relative to "now", so merging deltas is subtle, and the git-log crawl is the cheap half anyway (no TS parse). TS-symbol/import/precise-ref re-extraction — the expensive half — is what goes incremental.
- ~~**Git hooks.** `plex install-hooks` writes `post-merge` / `post-checkout` / `post-rewrite` → `plex index --incremental`, so the graph self-refreshes on pull/checkout/rebase.~~ **Removed in ADR-36** — the review-time drift-refresh (above) already keeps the graph fresh, so the hook was redundant, and writing into `.git/hooks` is setup friction the zero-setup pitch can't justify.
**Consequences.** Pay the big parse cost once; keep fresh in O(changed files); the blast radius stops silently drifting and new files stop being invisible. Workspace/runtime couplings that static resolution misses remain covered by co-change (ADR-06). Incremental indexing is Kùzu-only (no FalkorDB), so it is safely covered by the tsx integration runner (ADR-16/17). ~~*Deferred:* truly incremental co-change.~~ **Done in ADR-26.**

## ADR-26 — Truly incremental co-change ✅ (built, M8)
**Context.** ADR-25's incremental index still recomputed co-change **fully** (re-crawl all `maxCommits` of history) — the cheap half, but not actually incremental. The blocker was recency decay: weights are relative to "now", so naively merging deltas drifts.
**Decision.** On an incremental update, crawl only `storedSha..HEAD` (the new commits) and **merge** their contributions onto the stored pairs. Two observations make this exact without epoch bookkeeping: (1) `aggregateCoChange` clamps age with `Math.max(0, now−ts)`, so the just-landed commits contribute at **full recency** regardless of the reference; (2) decay **re-baselines on every full build**, and incremental only *adds* recent evidence. Pruning is preserved: increment pairs reaching `minPairCount` within the window **create-or-accumulate** (`MERGE … ON CREATE/ON MATCH`); sub-threshold pairs **only accumulate into already-stored pairs** (`MATCH … SET`), never creating singletons — so the ADR-06 N² denoising stands.
**Consequences.** Incremental index now skips *both* the TS re-parse (ADR-25) and the full git-history crawl — co-change refresh is O(new commits). The one residual imprecision: a pair below threshold in *every* window stays pruned until a full rebuild (by design; self-heals on `plex index` without `--incremental`). Old pairs keep their last-full-build decay (not re-decayed each increment), which is the intended "recency relative to the last full index" model.

## ADR-27 — Semantic waiver suppression ✅ (built, M8)
**Context.** Waivers matched by **exact identity** (file+line, or normalized-title equality). Line-scope breaks the moment code moves; pattern-scope breaks when the finding is reworded — so "I said ignore this issue" resurfaces a round later, the exact gap raised when designing the brain. M6 made change-attribution embedding-based; waivers should use the same signal.
**Decision.** A pattern/category-scoped waiver also stores an **embedding** of the waived finding (title + note). At rank time, findings are embedded and a waiver matches **semantically** when cosine ≥ `0.82` — *complementing*, not replacing, identity matching. Precise scopes (`line`/`file`) stay exact (they're locational on purpose). Best-effort and back-compatible: it needs a provider (already required in the M6 review flow) and the default threshold (1.01) disables semantic matching so the pure matcher is unchanged when no embeddings are supplied. Stays within ADR-02 — a waiver is a *fact* (the user's verdict), not replayed reasoning.
**Consequences.** A waived issue stays waived across rounds despite line drift and rewording; the long-standing "I said ignore it" leak is closed. The match is in the pure `waiverMatches` (vectors in — unit-tested); the engine embeds findings + waive-time titles at the boundary. Requires embeddings (already mandatory for the brain — ADR-13/22).

## ADR-28 — Autonomous review; outcomes inferred from response, not prompted ✅ (built, M9)
**Context.** The review loop asked the user to accept/reject/waive each finding — an interactive gate that breaks flow and (worse) re-introduces bias by quizzing the user mid-review. The right model is the one the PR-responder ecosystem already implies: review **autonomously**, then learn from the user's *actual response* (did they fix it? did they push back?).
**Decision.** The reviewer **submits findings and stops** — it never prompts for a verdict. Outcomes are recorded autonomously from **explicit signals only** (the user's chosen policy — silence is not a signal):
- **Fix → `accept`, automatic.** On the next round, a prior-round finding **addressed** by a change-since is auto-recorded as `accept`/fixed and marked `outcome=fixed` so it's evaluated once. This rides the *existing* `get_review_context` call — re-reviewing a PR after pushing fixes closes the loop; no extra step.
- **Dismissal → `reject`, agent-driven.** An explicit "intentional / won't-fix" stays the agent/responder's call via `record_outcome` (intelligent classification, ADR-20 spirit — no engine keyword heuristic).
- **Silence → nothing.** A finding the author simply hasn't reached is never inferred as a reject.
Auto-accepts feed the existing `consolidate_knowledge` reweighting.
**Consequences.** Reviews never interrupt to ask; the feedback loop runs off real behavior; no false negatives from silence or brittle keyword-guessing. The decision (`findingAddressed` / `findingAddressedAt`) is pure + unit-tested; the brain stores findings per round (M6) and marks their inferred outcome. Requires the brain; embeddings are now *optional* (ADR-30) — the semantic half degrades, the locality half still reconciles. E2E-verified under node (`pnpm test:brain`: inject a finding → address it with a commit → next review auto-accepts and marks it fixed).
**Refinement (locality — fixes a silent miss).** Matching the finding's *title* embedding against a *changed-region* embedding is lossy: a fix that **restructures** the flagged code (wraps a loop in try/catch, moves the flagged entity lines) reads nothing like the bug's title, so the cosine never clears `0.6` and a genuinely-fixed finding is never accepted (observed live: `reconcile` returned `checked: 9, accepted: 0` against 4 real fix commits). So "addressed" is now **semantic OR locality**: a change in the finding's *own file* within a windowed range of its line counts too (`findingAddressedAt`, default semantic ≥ `0.6` / line-window `30`). Recall-biased on purpose — a missed accept loses the learning signal entirely and re-surfaces a fixed finding, while a rare false accept only mildly over-reinforces a pitfall. Locality needs no embeddings, so reconcile now works (semantic half degraded) even without a provider (ADR-30).
**On-demand `reconcile`.** The same fix-inference is exposed as a standalone, **service-free** primitive (`reconcileOutcomes` / MCP `reconcile_outcomes` / `plex reconcile`) over the embedded Kùzu brain (ADR-30): check a target's open findings against what's been pushed since and record the accepts, *without* a full review. This is the right home for "check after a push" — call it from the responder skill (on PR-thread resolution it can also just `record_outcome accept` directly) or a CI `on: push` step. And it need not be invoked at all: the **review itself** runs the same fix-inference on its next pass (ADR-28's auto-accept), so a re-review closes the loop with no responder and no hook. Deliberately **not** a `pre-push` git hook: that would run embedding calls on every push and could block/fail it. (Git-hook auto-index was itself later removed entirely — ADR-36.)

## ADR-30 — Brain on Kùzu; FalkorDB removed; embeddings optional; auto-index ✅ (built, M11)
**Context.** FalkorDB was the only thing forcing a *service* (Docker) and was the entire reason for the isolated-worker indirection and the Kùzu+FalkorDB SIGSEGV class (ADR-16) — including the fragile "how many Kùzu opens before the worker spawn" tuning. For a tool whose whole pitch is "easy, local-first, single-command install," that's the biggest friction and the biggest bug surface.
**Decision.** Move the per-PR brain into an **embedded Kùzu** database (`<repo-data>/brain.kuzu`) — the same engine as the code graph. `Round`/`Finding`/`Verdict`/`Comment` are typed nodes keyed by review target (`outcome=''` sentinel for un-resolved findings; `MERGE … ON CREATE/ON MATCH` for upserts). A `Brain` handle is opened **once per review** and shared across all its brain I/O (avoids reopening the same Kùzu file concurrently). **FalkorDB is removed entirely** (dependency, worker, Docker, `falkordb` config, `PLEX_FALKORDB_URL`, `db:up`/`--falkor`). Two consequences fall out and are adopted:
- **Embeddings are optional** for review. Without a provider the brain still records rounds/findings; only the *semantic* signals (changed-without-feedback + fix inference) are skipped. No hard "key required" gate (relaxes the M6 requirement; ADR-13 still governs the knowledge write paths).
- **Auto-index on first review**: a never-indexed repo is built in an *isolated child process* (so the review process opens Kùzu only for the neighborhood + brain), so `plex init`/`plex index` aren't required per-repo.
**Consequences.** No Docker, no service, no `pnpm db:up`; install is genuinely "single command, done" and a review runs against any git repo with zero setup (better with a key). The ADR-16 cross-engine SIGSEGV class is **gone** (the brain E2E and reconcile now run as ordinary Kùzu tests). **Supersedes** the FalkorDB-required stance of ADR-07/ADR-22 and retires ADR-16's worker (Kùzu+Kùzu share a process fine; the tsx open-limit of ADR-17 still applies, so tsx scenarios stay ≤2 Kùzu opens — the brain E2E remains a node check). *Trade-off (accepted):* the FalkorDB Browser viz is dropped; the durable graph is inspectable in Kùzu Explorer instead.

## ADR-31 — `awareness` findings + `acknowledge` ✅ (built, M12)
**Context.** A reviewer comment like *"two `payment_confirmed` emit sites — confirmed intentional, flagged for awareness"* is **valuable** (catching a possible double-fire), but the taxonomy forced it into `nit` (trivial) and the autonomous loop treated "confirmed intentional, no code change" like a dismissal → `reject` + semantic waiver → suppressed into silence. Both are wrong: surfacing the flag *is* the value, and you want it re-checked so a *third* site gets caught.
**Decision.** Two additions on the existing axes (ADR-04/27):
- **`severity: 'awareness'`** — a distinct intent ("noticed, worth confirming"), not a defect and not a nit. It triages into its own **`awareness`** bucket (surfaced, ranked separately) and is never folded into the defect stream or auto-suppressed by prevalence.
- **`verdict: 'acknowledge'`** — for an awareness flag confirmed *intentional*. It records a **semantic waiver** (embedding of the flag) so the same flag stops surfacing, but — unlike `reject` — it does **not** down-weight the knowledge that raised it (the catch was *good*). Because the match is semantic (ADR-27), a *materially changed* instance (a 3rd site → different text → cosine below threshold) **re-surfaces**. Chosen behavior: acknowledge → silent until it changes.
- **Awareness is excluded from auto-accept** (the ADR-28 fix-inference). An awareness item isn't a defect to be "fixed", so inferring `accept` from a nearby change is semantically wrong — and worse, it *pre-empts* the acknowledge→waiver path (a real case: a try/catch wrapping the flagged lines made fix-inference auto-`accept` an intentional `await`-in-loop awareness flag via file/line locality, so it re-derived and re-surfaced the next round instead of going quiet). So `recordFixAccepts` skips `severity:'awareness'` — only an explicit acknowledge/reject resolves it, and that's what makes acknowledge the governing mechanism for "silent until materially changed."
**Consequences.** Awareness flags are first-class (surfaced in "Worth confirming", never buried as nits); confirming one is "good catch, intentional" not "you were wrong"; the loop neither nags nor forgets. The agent classifies `awareness`; the responder records `acknowledge` (not `reject`) for confirmed-intentional flags. Implemented across core types, `findings` (triage bucket + the unchanged semantic matcher), `verdicts`/`knowledge` (acknowledge → embedded waiver, no down-weight), and the MCP/CLI/agent/responder surfaces.

## ADR-32 — Worktrees seed their code graph from the base (default-branch) worktree ✅ (built)
**Context.** Graphs are keyed by absolute path (ADR-30), so every git worktree/branch already gets its *own* `graph.kuzu` and the base is never modified — isolation is correct. But a fresh worktree did a **full re-parse** (~95s on a big monorepo), which hurts a worktree-per-task workflow.
**Decision.** When indexing a path that has no graph yet AND is a *secondary* worktree, pick the **base** to seed from — the worktree on the repo's **default branch** (`origin/HEAD`, else `main`/`master`) if one is checked out, else the primary worktree — provided its graph already exists. Then: **refresh the base to its own HEAD**, **copy** the base graph, and run an **incremental update** applying only this branch's diff (`baseIndexedSha..branchHEAD`). The base is read-only to the copy — N worktrees can never affect it. Falls back to a full build if the copy/incremental fails.
**Consequences.** A new worktree is **seconds, not a full parse** (copy a single-file `graph.kuzu` + extract only the changed files); reviews/auto-index benefit automatically (the auto-index spawns `plex index`, which seeds). One durable base graph on the canonical branch, kept fresh, cheaply cloned per branch, never mutated by any worktree — exactly the intended model.
**Two hard-won implementation constraints (ADR-17).**
- The base refresh runs in an **isolated child** (`plex index --incremental`), *not* an in-process recursive call. Opening the base's Kùzu **and** the copied graph in one process is two opens → a deterministic **SIGSEGV**. The child keeps the seeding process to a single Kùzu open. (This was the first cut's bug; covered now by `scripts/worktree-seed-check.mjs`.)
- A **rare** native Kùzu crash can still fail a single seed (opening a freshly-copied DB). `indexIsolated` therefore **retries once** — the retry of a full build self-heals because a partial graph makes the next `plex index` skip the seed and fall to `buildCodeGraph`, which clears the dir first. So the review flow is resilient; a one-shot manual `plex index` that crashes is simply re-run.
**Tests.** tsx `worktree-seed` scenario (seed mechanic + path/sidecar isolation, ≤2 Kùzu opens) and the node `pnpm test:worktree` E2E under the shipped runtime (self-refresh of a stale base, default-branch selection over the primary, and the no-SIGSEGV guard the tsx layer can't exercise).

## ADR-33 — Drop the Kùzu Explorer; zero Docker ✅ (built)
**Context.** ADR-30 removed FalkorDB to go fully embedded, but kept one Docker artifact — a `docker-compose.yml` running the **Kùzu Explorer** to inspect the durable graph (the trade-off note in ADR-30: "inspectable in Kùzu Explorer instead"). In practice nobody reaches for a raw graph browser, and a lingering `docker-compose.yml` + `.env`/`.env.example` quietly contradicts the "no Docker, no services" pitch — and it *invited the mistake of putting an embedding key in `.env`*, which Plex never reads.
**Decision.** Remove the Explorer entirely: `docker-compose.yml`, `.env`, `.env.example`, the `pnpm ui:kuzu` script, and the doc references. The only graph/review visualization that stays is `plex review --html` (`reviewContextToHtml`) — a single self-contained Cytoscape file per review, no service. **Supersedes** ADR-30's "inspectable in Kùzu Explorer" trade-off.
**Consequences.** The repo now has **zero Docker** — `grep -ri docker` returns only the "no Docker" claims and the historical ADR-30/M11 records. Config lives solely in `~/.plex/config.json` (via `plex init`) + process env; there is no `.env` to mislead. If interactive graph inspection is wanted later, it should be a real built-in UI, not a detached container (see `docs/design/shared-brain.md` for where a viz would fit).

## ADR-34 — Auto-comment: post the review back to the PR ✅ (built)
**Context.** A review that only prints findings in the terminal stops short of the PR lifecycle — the findings never reach the PR where the author and other reviewers see them, and they can't feed the `pr-review-responder` triage loop without being real GitHub comments. We want Plex to optionally act as a review *bot* (like Copilot), then hand off to the responder so the author decides.
**Decision.** When reviewing a PR (`source: 'pr'`) and **opted in** (`autoComment`, default off; `PLEX_AUTO_COMMENT` / `~/.plex/config.json`), `submit_findings` (via `rankReviewFindings`) posts the ranked stream to the PR as **one** GitHub review (`event: COMMENT`, never approve/request-changes): **inline comments** on findings that land on changed lines + a **summary body** for coupled/blast-radius findings and a "worth confirming" awareness section. The build is a **pure function** (`buildReviewPayload`, unit-tested) over the ranked stream; the `gh` call is isolated in `ingest/postPrReview`. **Deduped against prior rounds** via the brain's `priorFindings` (captured before the round write), so re-reviews post only what's new — no comment spam. `nit`s post by **default** (they carry value); `PLEX_AUTO_COMMENT_SKIP_NITS` opts out. Suppressed/waived findings are never posted. Posting is **best-effort** — a `gh` failure never breaks the review.
**Consequences.** Closes the loop: reviewer posts → `pr-review-responder` reads the comments, shows the assessment table, applies fixes/replies on your `go`, and `reconcile_outcomes` feeds the outcomes back to Plex. The agent must NOT post itself (Plex did). Non-PR reviews and opt-out installs are unchanged (terminal-only). The line-anchoring is GitHub-native (inline only on diff lines; everything else folds into the body).

## ADR-35 — Supply-chain hardening posture; CI/OIDC release deferred ✅ (decided)
**Context.** npm is under active self-replicating-worm attack (Shai-Hulud 2025; IronWorm + the Miasma/"Phantom-Gyp" campaign in 2026 — the latter hides execution in a `binding.gyp` to bypass install-script scanners, and reached Microsoft's Azure GitHub org via a compromised contributor account). As `@sshanzel/plex` heads to npm, the question is what hardening actually maps to these *mechanisms* (token/credential theft + execution on install) vs. theater.
**Decision.** Defense is already centered on the right vector: our published package runs **no** install code (`files`-whitelisted `dist`/LICENSE/README, no `pre/postinstall`, no `binding.gyp`), and pnpm `onlyBuiltDependencies` **default-denies** dependency install *and* native (`node-gyp`/`binding.gyp`) builds except `esbuild`/`kuzu` — blocking both the postinstall vector and the Phantom-Gyp bypass for non-allowlisted deps. Plus lockfile SRI, `overrides`, Dependabot, npm 2FA-passkey, and a **3-day pnpm `minimumReleaseAge` cooldown** (no dependency version installs until 3 days post-publish — the worms land malice in builds within minutes, before the registry yanks it). The remaining hardening is **written but dormant** (single maintainer, no users yet): SHA-pinned, least-privilege GitHub Actions for a quality gate (`ci.yml`, manual) and a **tokenless OIDC Trusted-Publishing + provenance** release (`release.yml`, tag-fired); and npm 2FA set to "authorization and writes". Full posture + residual risk (compromised *allowlisted* dep; malice in a dep's *runtime* code) live in [`SECURITY.md`](../../SECURITY.md).
**Consequences.** Most of the protection is in place now with no process overhead; the rest is one edit away (uncomment CI triggers / register the Trusted Publisher) when there are users. First publish is manual (with 2FA, creates the package); releases after that are tokenless + provenance-signed via CI. Workflow files are inert until their triggers fire — committing them changes nothing until CI is opted in or a `v*` tag is pushed.

## ADR-36 — Drop the git-hook auto-index; the review is the trigger ✅ (decided)
**Context.** ADR-25 shipped `plex install-hooks` (`post-merge`/`post-checkout`/`post-rewrite` → `plex index --incremental`) to keep the graph fresh between reviews, and `plex init` installed it automatically. Two problems. (1) **Friction + invisibility**: letting a tool write into `.git/hooks` is too much to ask of a "single-command, zero-setup" pitch — and the install leaves *no tracked trace* (`.git/hooks` is untracked, uncommitted, in no config, and doesn't travel to teammates on clone), so it silently mutates local state. "Seamless" and "spooky" are the same property. (2) **Redundant**: ADR-25/30 already auto-refresh the graph on drift **at review time** in an isolated child (`assembleReviewContext`: read sidecar `headSha` → `commitsBehind` → incremental refresh). The hook only moved that same refresh earlier (to pull/checkout) — a marginal latency head-start for real cost in setup, surprise, and surface.
**Decision.** Remove the git-hook feature entirely: `engine/hooks.ts` (`installHooks`/`uninstallHooks`) + its tests, the `plex install-hooks`/`uninstall-hooks` CLI commands, and the `plex init` auto-install. **The review is the trigger** — staleness is handled lazily, where it's needed, by the existing drift-refresh (ADR-25); embeddings stay the one *optional* value-add layer (ADR-30). **Supersedes** the "Git hooks" part of ADR-25 (the staleness signal + incremental index it shipped remain). Already-installed hooks in user repos are orphaned but harmless — they call the still-valid `plex index --incremental`; remove by hand from `.git/hooks` if wanted.
**Consequences.** Setup is "point an agent at the MCP and review" — nothing writes into `.git/`. The graph is never silently stale (the review refreshes it); the only thing lost is the pull-time head-start, repaid as a one-time incremental at the next review. Git hooks remain a future option *iff* a real workload shows the review-time refresh is too slow — and then it belongs behind an explicit, visible opt-in, never `init`.

## ADR-37 — Remove `plex.md`: knowledge is learned, not hand-authored ✅ (decided)
**Context.** `plex.md` (ADR-09) was the human-authored steering surface, reached two ways that never composed: (1) a **verbatim feed** — the whole file read raw into `reviewerMd` and handed to the agent every review with only "honor it," paying a per-review token cost for an always-considered *guarantee it never actually enforced* (the prompt never told the agent to confirm each rule holds); and (2) a **manual seed** (`plex seed`/`seed_knowledge`) that parsed bullets into pitfalls (title = trigger = why), so a kept-and-seeded file reached the agent **twice**, with muddy provenance. No structure, no scoping, no severity control, no lifecycle — half-baked on both halves.
**Decision.** Remove everything whose **sole purpose** was `plex.md`, and (second pass) the dead promotion/external machinery it was entangled with. Gone: the verbatim feed (`loadReviewerMd`/`reviewerMd`); markdown seeding (`seedFromMarkdown`/`parseMarkdownPitfalls`/`seedKnowledge`, the `seed_knowledge` MCP tool, `plex seed`); the **whole promotion surface** (`proposePromotions`/`getPromotions`/`propose_promotions`/the `plex promote` rules output) — both its markdown half *and* its graph → ast-grep rule stubs, which only ever emitted `pattern: TODO` scaffolds for an external runner that was never wired; and that prober itself (`detectExternalTools`/`external.ts`, zero callers). `plex promote` → renamed `plex consolidate` (it now only recomputes confidence). **Keep** the learning loop: `recordIncident`, `consolidatePitfalls`/`consolidate_knowledge`, all retrieval, analysis. Knowledge is populated **only by analyzing PR history + the review feedback loop**.
**Consequences.** Smaller surface (15 → 13 MCP tools), no wasted per-review tokens, one provenance story (learned), and the deterministic layer is honestly just its built-in TS-AST rules. The cost is the loss of the only *committed, shared, version-controlled* steering surface until its replacement lands: **`plex.json`** — a structured, repo-committed review-policy file (string-or-object rule array + an eslint-shaped `deterministic` section that *defers* to the linter you already run + always/contextual tiers) — is the planned successor and sits in the backlog; it's also the proper home for user-authored deterministic rules (Plex respecting your existing ast-grep/eslint, not re-running it). **Supersedes ADR-09.** `IncidentSource`'s `'seed'` member was dropped too (runtime-safe: TS types are erased, so a stored `source: 'seed'` incident still deserializes as a plain object). `Pitfall.tier` is left as inert metadata (the analysis pipeline still sets it; nothing reads it) — a natural hook if real rule-execution ever lands.

## ADR-38 — Naming: `analyze` (feature) over `@plex/distill` (pipeline) ✅
**Context.** Turning a team's PR-review history into reusable pitfalls needs a name. A product verb that implies *extracting value out of a subject* reads as invasive — even though Plex only ever reads your *own* repo's *own* review comments, locally. The unease is about the **product verb**, not the underlying technique.
**Decision.** The feature is **`analyze`** (CLI `plex analyze`, MCP `analyze_scan` / `analyze_history`, engine adapters `analyzeRepo` / `scanForAnalysis` / `addAnalyzedPitfalls` / `AnalyzeOptions` / `AnalyzeState` / `ReviewCluster` in `engine/src/analyze.ts`). The clustering + LLM-distillation **technique** is a separate package, **`@plex/distill`** (`distillHistory` / `scanHistory` / `distilledPitfallId` / `DistillResult` in `pipeline.ts`). Config lives under **`config.analyze`** (`AnalyzeConfig`); the incremental cursor is **`analyze-state.json`**; incident provenance is `source: 'analyzed'` with id prefixes `inc:analyzed:` / `pf:analyzed:`.
**Consequences.** The user-facing surface reads as the user's own history being reviewed for their benefit, not harvested. The feature/technique split keeps the product word (`analyze`) distinct from the algorithm (`distill`): the `analyze` feature runs the `distill` pipeline. Other commands unaffected.

## ADR-39 — Learned suppression (negative knowledge) on a Wilson basis ✅ (decided)
**Context.** The feedback loop only learned *positives*. An `accept` became an `Incident` → `consolidatePitfalls` → confidence, scoped repo/global. A `reject`/`waive` produced only an instance waiver + a brain `outcome` flag — **no incident, no consolidation, no scope** — and `pattern-repo`/`category-global` were waiver scopes **nothing ever produced**. So a deterministic rule with no pitfall backing (e.g. `no-console`, the since-removed `no-await-in-loop`) re-fired at full strength no matter how often it was dismissed: the "I keep turning this down and still see it" complaint. Two hard constraints from the product owner: **C1** — a dismissal must be *weighted*, never a one-click permanent kill (a "fix it next PR" is not "this is wrong"); **C2** — global promotion must be *language-aware* (a multi-language user must never get a TS rule applied to a Python repo).
**Decision.** A suppression is a first-class **negative pitfall** flowing through the SAME incident → consolidate → scope loop as a positive one (`docs/design/negative-knowledge.md`). (1) **Producer** (`learnSuppression`, called from `submitVerdict`): a reject/waive of a finding with a stable key (parsed from a `det:<rule>` id, or an explicit pattern) records a *confirming* incident on a repo-scoped negative pitfall; an accept/fix records a *refuting* one. Retry-deduped by `firstOfKind`. (2) **Scoring unified on the Wilson score lower bound** (Wilson 1927) for BOTH polarities — this retired the hand-tuned Beta prior, `REJECT_COST = 1.5`, and `outcomeWeight` 1.5s. The suppress/demote call is `suppressionTier(dismissals, corrections)`: `suppress` when the 95% Wilson lower bound ≥ the 0.5 majority pivot (≈4 consistent dismissals), `demote` at the 1σ level (1–3) — **no hand-tuned floors, only textbook confidence levels**, so C1 holds *by construction* (a lone 1/1 has too wide an interval to act on). (3) **Ranking** gains a `demoted` triage tier (between `convention` and `suppressed`); `loadSuppressions` computes the tier **live** from incident counts, so a dismissal takes effect next review without a `consolidate` run. (4) **C2 promotion** is computed live in `loadSuppressions`: a key that earned `suppress` in ≥ `PROMOTE_MIN_REPOS` (2) distinct repos *of the same language* generalizes to `global@lang` — grouping by language means TS and Python never merge, and because a deterministic tag is itself language-bound a promoted decision only ever matches that language's findings; **no language-blind auto-promotion** (agnostic-global stays certified-only). `PROMOTE_MIN_REPOS` is a deliberate *policy* floor (independent-project corroboration is a risk choice), explicitly not statistical. **Provenance:** brain `Verdict` nodes hold the raw per-round dismissals; each `Incident.note` records the verb (`reject`/`waive`) the scoring flattens; the `findings_submitted` audit event records the active suppressions with their counts + tier — "why is this rule listed?" answerable end to end. **Interim:** the up-front context waiver filter (which primes the agent) honors only `waive`/`acknowledge`, never `reject` (a reject is the weighted path now).
**Consequences.** Dismissing a deterministic rule finally teaches Plex — weighted, reversible (an accept pulls the Wilson tier back down), and generalizing across same-language repos. One estimator (Wilson) for positive and negative pitfalls; the positive path lost the `reverted` 1.5 bonus (it's now a plain confirm) and runs more conservative confidences (a 2-0 record ≈ 0.34, not 0.75) — acceptable because pitfall confidence is mostly informational (retrieval ranks by cosine). **Deliberately deferred** (each would reintroduce a tuning constant the Wilson move removed, so not built unsilently): **decay** (so a `reject` fades vs a `waive` persisting — needs a half-life) and a **re-surface probe** (needs a cadence) — note recovery already works without a probe since `suppressed` *sinks to the bottom of the stream, it is not deleted*; and **first-principles suppression** (a non-deterministic finding has no stable key — needs semantic matching, a separate feature). `outcomeWeight` stays exported (tested) but is now unused by consolidation (`betaPosteriorMean` was removed entirely). Promote the design note's open items when a real workload justifies the constants.

## ADR-40 — Revert worktree read-only graph sharing; copy + store in-workspace (Kùzu read-only SIGSEGVs on Linux) ✅ (decided)
**Context.** A post-ADR-32 optimization (commit `130b415`, "share base graph read-only instead of copying") replaced the worktree graph **copy** with a **read-only shared open** of the base's `graph.kuzu` (`new Database(dir, 0, true, true)`) — no per-worktree copy. It turned CI **red on every run** from the moment it landed (green at `v0.3.3`, the commit before; red ever since) and, worse, crashes **real Linux worktree reviews** (`review.ts` opened the base read-only on every review). Root cause, confirmed three ways: (1) CI bisect pins it to that exact commit; (2) `brain-check` (normal open) passes on Linux amd64 while only the read-only path crashes; (3) a minimal repro segfaults on Linux. **Kùzu 0.11.3's read-only `Database` open SIGSEGVs on Linux**, and 0.11.3 is the latest stable — no upstream fix to upgrade to. (An interim CI fix added a `SIGSEGV` retry to the index spawns; it greened indexing but couldn't cover the review-time read-only open.)
**Decision.** **Revert to copying** (ADR-32 original): a secondary worktree gets its **own** `graph.kuzu` (a copy of the base + its diff applied via incremental update) and opens it **normally** — never read-only. No Kùzu read-only open anywhere. Considered and rejected: a graph **server** (FalkorDB et al.) for real concurrency — it reverses the embedded, "nothing-running" principle (ADR-30) to solve a niche (worktree) case, and FalkorDB had its own SIGSEGV history here. **Additionally, relocate a worktree's data dir IN the worktree** (`<worktree>/.plex`, self-gitignored by `ensureDataDir`) instead of centralized `~/.plex/repos/<id>` — `repoPaths` detects a linked worktree (its `.git` is a file) and uses the in-workspace path. So the copied graph (the big artifact) and the worktree's brain **die with the worktree folder** — no centralized orphan to garbage-collect, which is the cleanup the copy approach otherwise needs.
**Consequences.** Linux worktree reviews work; CI is green. A worktree pays a single-file graph copy (cheap vs a full re-parse) and its data self-cleans on `git worktree remove`. The copy-SOURCE selection (`baseWorktree`, default-branch base) is now purely a perf optimization — correctness is guaranteed by the incremental refresh regardless of which base is copied (so the worktree-seed checks assert "own graph, normal open, no SIGSEGV", not a precise source). The `SIGSEGV` retry stays as belt-and-suspenders. **Supersedes the read-only-sharing part of `130b415`** (its orphan-detection + repo-path sidecar are kept). File an upstream Kùzu issue with the repro so read-only sharing could return if fixed. **ADR-32's README already described the copy approach** (the read-only revision never updated it), so the docs now match the code again.

## ADR-41 — Suppression decay + first-principles suppression ✅ (decided)
**Context.** ADR-39 shipped learned suppression but deferred three pieces: dismissals were timeless (a year-old `reject` counted like today's) and `waive` == `reject` in scoring; only deterministic rules could be suppressed (the agent's own first-principles findings have no key); and a wrong suppression needed a recovery path. **Key insight:** these aren't independent — **decay is the keystone**. If each dismissal contributes a recency-decayed weight instead of a flat 1, the effective sample size shrinks as evidence ages → the Wilson interval widens → the tier slides `suppress → demote → surface` on its own. So decay delivers the verb distinction (different half-lives) AND the re-surface behavior, and the separate probe becomes redundant.
**Decision.** (1) **Decay** — `loadSuppressions` weights each dismissal by `0.5^(ageDays/halfLife)` (pure `recencyWeight`/`decayedCounts` in `@plex/knowledge`), feeding the *decayed fractional* counts straight into the unchanged `suppressionTier` (Wilson takes plain numbers; the small-sample conservatism that protects C1 is preserved — a lone fresh `reject` still can't suppress). **Verb-specific half-life**: `reject` ("not now") fades fast, `waive` ("this is wrong") persists; **corrections (accept/fix) are durable** (full weight — the user acting on a finding is permanent evidence it was real, and must not fade and let a stale suppression creep back). The verb is the authoritative new `Incident.verb` field (`outcome:'rejected'` flattened the two). **Clock = wall-time** (incidents carry `ts`; **review-count** is the documented future alternative — it would need a per-incident round number + brain coupling — left as a hook). Config `suppression: { rejectHalfLifeDays: 30, waiveHalfLifeDays: 365 }` — the accepted tuning knobs. (2) **First-principles suppression** — a finding with no tag/pattern is keyed by its **title embedding**: the producer embeds the dismissed title and **match-or-mints** against existing embedding-keyed negative pitfalls by cosine ≥ `adaptiveFloor(0.82,…)` (mirrors `inferPitfallId`; conservative — bias toward minting over polluting another's evidence); the read path includes embedding-keyed negatives and `rankReviewFindings` routes them through the **existing semantic-waiver path** as synthetic `pattern-repo` waivers carrying the embedding (`waiverMatches` already does the cosine match — **zero new code in the pure `@plex/findings` package**). Embedding-gated (no provider → no first-principles learning; deterministic suppression unaffected). Semantic suppressions act only at the `suppress` tier (a tagless `demote` has nothing to explain it). (3) **Re-surface probe — DROPPED**: subsumed by decay (an aged suppression self-resurfaces), and `suppressed` already *sinks rather than deletes* (`rank.ts`) so a wrong suppression is always recoverable. A probe would reintroduce a cadence constant ADR-39 avoided.
**Consequences.** The negative-knowledge loop is complete and *alive*: dismissals age and self-correct, the waive/reject distinction is real, and the agent's own findings are suppressible. Tradeoffs (carried from the design): **fractional Wilson** is a heuristic, not calibrated coverage — but the monotonicity we rely on holds, and the "~4 dismissals → suppress" intuition now means "~4 *recent full-weight* dismissals"; **cross-repo promotion is now non-monotone** (a quiet repo de-promotes — correct); **first-principles needs embeddings** (a key-less install can't learn it; the 0.82 floor controls double-count-vs-merge, same tradeoff as `inferPitfallId`). Builds on `docs/design/negative-knowledge.md` + `docs/design/knowledge-decay.md`.

## ADR-42 — Positive-path knowledge decay (recency reinforcement + retrieval tilt + pruning) ✅ (decided)
**Context.** ADR-41 shipped recency decay for the *suppression* (negative) path, but the *positive* knowledge base still only grew and only strengthened: `consolidatePitfalls` returned a pitfall unchanged when it had no new incidents, so a one-off lesson kept its confidence forever and kept being retrieved; nothing aged out a stale lesson or pruned the store. `docs/design/knowledge-decay.md` tracked the broader vision; this builds its positive/retrieval half.
**Decision.** Mirror the ADR-41 model on the positive path, reusing `recencyWeight` (no new math). (1) **Recency-weighted reinforcement** — `consolidatePitfalls(store, decay, now = new Date())` weights each incident's confirm/refute contribution by `0.5^(ageDays/halfLifeDays)` before the **unchanged** `wilsonLowerBound` (which already takes fractional counts), so a lesson that stopped recurring fades. (2) **`lastReinforcedAt`** (new `Pitfall` field, set in the same fold-in as `incidentIds`) is the single field retrieval reads. (3) **Retrieval recency-tilt** — `rankAndSlim` multiplies each score by `max(retrievalTiltFloor, recencyWeight(age, halfLife))` before the `minScore` cut, so a stale pitfall ranks lower (and can drop out) **without mutating stored confidence** (read-only, reversible); the floor keeps an old-but-real lesson visible. (4) **Pruning** — drop a pitfall iff `refutes > 0 AND decayedConfidence < pruneFloor AND quiet > pruneMinAgeDays AND has incidents AND non-repo-scoped`; the **`refutes > 0` gate is load-bearing** — the decayed Wilson lower bound penalizes sample *thinness* regardless of confirm rate, so without it a real-but-rare NEVER-refuted lesson (1 confirm, >1y old → Wilson ≈ 0.06) would be deleted despite a 100% confirm rate. Only a lesson the user has actually *contradicted* is a prune candidate; a never-refuted dormant one is handled by the retrieval tilt (ranks low), not deletion. **Only the derived pitfall is removed — `incidents.jsonl` is never touched**, so provenance survives and re-analysis can regenerate it. Config `decay: { halfLifeDays: 365, retrievalTiltFloor: 0.5, pruneFloor: 0.1, pruneMinAgeDays: 365 }` (+ `PLEX_DECAY_*` / `~/.plex/config.json`). Determinism: `now` injected, never `Date.now()` in the pure paths.
**Consequences.** The KB sharpens over time instead of monotonically piling up. Invariants preserved: **ADR-05** — the tilt multiplies the *retrieval score* only and never reads `prevalence`; ranking enforces prevalence-by-severity independently, so a widespread real bug is never decayed/pruned away (it stays high-confidence while it keeps recurring). **ADR-11** — a zero-incident analyzed prior keeps its prior confidence and is **prune-exempt** (it never had a chance to be reinforced). **Idempotent** at a fixed `now`; **undated incidents → weight 1**, so the frozen quality-floor corpora (`retrieval-quality` recall 7/8, `ranking-quality` nDCG 0.9) stay green untouched. **Decay only takes effect when `consolidate` runs** — which nobody runs on `main`; ADR-43's maintenance worker runs it so this isn't dormant. Builds on `docs/design/knowledge-decay.md` (now "built" for the positive path).

## ADR-43 — Background maintenance worker (loop closure + main freshness + decay + analyze) ✅ (decided)
**Context.** Every deferred Plex job — reconcile (loop closure), knowledge consolidation (incl. ADR-42 decay), base-graph freshness, review-history analysis — only ran on a **manual command**, and **nobody runs commands on `main`**. So after a PR merges, landed findings never reconcile, their incidents never reach the global KB (`~/.plex/knowledge`), the decay never fires, and `main`'s graph drifts (branch copies seed stale). The pr-responder *tried* to close the loop (`reconcile_outcomes`) but it dropped silently whenever the plex tools weren't loaded in-session — "it shouldn't be doing that." The brain is **per-machine, path-keyed** (a CI runner has an empty brain; a shared brain is a non-goal — `docs/design/shared-brain.md`), so none of this can live in CI; but the durable learning store `~/.plex/knowledge` is global and survives a merge — only the *tail* is lost.
**Decision.** A single **background maintenance worker** — an extensible job framework (`runMaintenance`/`sweepRepo`, `packages/engine/src/sweep.ts`) spawned best-effort + detached (`maybeSpawnSweep`: `spawn`+`unref`, debounced 10 min, no-op in dev/tsx) by ordinary Plex activity (end of `assembleReviewContext`, MCP `reconcile_outcomes`). It **maintains `main` as the canonical fresh base** — resolved from any worktree via `resolveMainRepoPath`; `main`'s data dir is centralized + durable, so targeting it **sidesteps the ADR-40 worktree-brain death**. Four idempotent, best-effort, single-flight-locked jobs: **Reconcile** (`brain.openTargets` → `diffSourceFromTarget` → `reconcileOutcomes` per target whose head advanced past a per-target cursor → auto-accept → global KB — the reliable replacement for the pr-responder bookkeeping); **GraphFreshness** (re-index `main` to HEAD on drift, in an **isolated child** — `indexIsolated`, never in-process: opening the code graph for a write while the brain is open SIGSEGVs Kùzu, ADR-17); **Consolidate** (run ADR-42 decay/prune — makes it *live*); **Analyze** (LLM/embeddings-gated; heaviest, daily). Review-start **base-staleness** self-heal: record `base.sha` at worktree seed; if `main` advanced and its graph is fresh, cheap re-seed inline; else spawn the worker **"tight"** (force, bypass debounce) and proceed on the current base (the accepted first-review-may-be-stale trade-off). **Idempotency is the safety invariant** (so a sweep never duplicates): reconcile rides `submitVerdict`'s learning-idempotency + the head cursor; consolidate is a pure overwrite; index is a no-op when fresh; analyze rides the `analyze-state.json` scan cursor; plus debounce + single-flight lock + per-job cadence.
**Consequences.** The loop closes automatically on the developer's machine without a manual `main` review, no git hooks (the trigger is Plex activity, not git events — **supersedes the git-hook temptation ADR-36 removed**), no service. The pr-responder's plex bookkeeping becomes belt-and-suspenders (the responder is an external plugin, so this only documents the supersession). The review-time inline reconcile/learning (ADR-36 step 8) is **untouched** — the worker is an *additional* background trigger, not a replacement. MCP tools (`reconcile_outcomes`/`consolidate_knowledge`/`analyze_*`) are kept as proactive escape hatches (non-load-bearing now); `record_outcome` stays (an explicit reject/acknowledge can't be inferred). **Limitations (accepted):** a linked worktree's own brain still dies with its folder (the worker targets durable `main`, doesn't cross worktrees); a branch's first review may use a stale base (the second self-corrects); the worker is per-machine. **Future, team-scale (documented, not built):** a cloud GitHub-bot review managing a **shared brain** dissolves the CI-empty-brain wall — the local worker is the local-first answer, the bot its team-scale complement (`docs/design/shared-brain.md`, `docs/design/maintenance-worker.md`).

## ADR-44 — Observed outcome signals + unified Wilson confidence (kill the manufactured confirm) ✅ (decided)
**Context.** The analysis path's `outcomeFor` was `prMerged ? 'accepted' : 'rejected'` — it **manufactured a confirm from a PR-level event**: every substantive comment on a *merged* PR was stamped `accepted` even when the author silently ignored it and merged anyway (we couldn't tell *applied* from *ignored-but-merged*). Three magic values fed the (otherwise principled, ADR-39) confidence estimator off the back of that assumption: (a) the binary merge⇒confirm label itself; (b) the analyzed-pitfall **initial confidence polynomial** `min(0.9, 0.3 + 0.1·n + 0.1·(merged/n))` (`distill.ts`); (c) the `add_pitfalls` **`0.6` default**. Meanwhile `outcomeWeight` (the `reverted` 1.5 / `accepted` 1 / else 0 table) was **dead code** — `confirmsAndRefutes` already treats accepted/fixed/reverted as *equal* confirms, so the design note's proposed "wire `outcomeWeight` back in so `fixed` > `accepted`" would have *reintroduced* the exact 1.5 magic ADR-39 deleted. The user's stake: **no arbitrary values unless they're the only option** — prefer algorithm- or reasoning-grounded ones. (Promotes `docs/design/outcome-signals.md`; the design note's "MVP" — keep `accepted` as the merged fallback — was rejected as a no-op that re-cements the manufactured confirm.)
**Decision.** Reframe richer outcomes as **correcting mislabeled evidence, not adding weights** — count only what we can observe, abstain otherwise; the estimator is untouched. (1) **`outcomeFor(c)` → observed label**: a **confirm (`fixed`)** only when the comment is **outdated** (GitHub nulled `position` because a later commit changed the hunk it was anchored to — `isOutdated`, the cheap, squash-merge-proof, already-in-payload "the flagged code was changed" signal) **AND** the PR merged; **everything else ABSTAINS** (`undefined`) — merged-but-unchanged, outdated-but-unmerged, or no anchor. Deliberately **no `rejected`**: historical analysis can positively confirm a pattern but never *refute* one (an unmerged PR says nothing about a comment's validity); refutation is the separate, intentional live-review `reject` path. An abstaining incident is still recorded for provenance but contributes **nothing** to the counts rather than fabricating a confirm. (2) **One confidence definition everywhere** — `confidenceFromOutcomes(outcomes)` = `wilsonLowerBound(confirms, confirms+refutes)`, the SAME estimator consolidation uses. It replaces the polynomial (`distill.ts`) AND the `0.6` default (`add_pitfalls` now derives it from the pitfall's provenance incidents). No observed fixes → 0 (honest floor: no positive evidence yet), rising conservatively as live reviews confirm (2/2 ≈ 0.34, never 1.0). (3) **Consolidation keep-prior on all-abstain** — `confirms+refutes === 0` (incidents exist but all uninformative) keeps the prior confidence, exactly like no-incidents, instead of `wilsonLowerBound(0,0) = 0` crushing a pitfall to a *confident-wrong* zero. (4) **Confidence now has teeth in retrieval** — `rankAndSlim` multiplies the cosine score by `max(tiltFloor, confidence ?? 1)`, a second bounded tilt beside the ADR-42 recency tilt (same floor): among similarly-relevant pitfalls the better-evidenced one wins, a missing confidence is neutral (1). The two tilts are independent axes that **compound** — each floored at `tiltFloor`, so a *stale-AND-weak* pitfall is discounted by up to `tiltFloor²` (0.25 at the default), which is intended (that combination should rank lowest). The floor bounds each axis, not the product: neither tilt zeroes a hit, but a low-cosine stale weak pitfall CAN drop below `minScore` (the same intended ADR-42 drop-out, now reachable via either axis) — so "never buries" means *never zeroed / never the sole reason a strongly-relevant hit is cut*, not "loses at most `tiltFloor`". (5) **Delete the dead `outcomeWeight`** (core) + its re-export/test.
**Consequences.** The manufactured confirm is gone: the confidence the learning loop trusts is grounded in an *observed code change*, not in "the PR merged." One Wilson definition of confidence spans distill → add_pitfalls → consolidate → retrieval, with **zero hand-tuned constants** in the path (the only knobs are the shared `tiltFloor` and the textbook Wilson levels). The richer signal *bites* because PR2's retrieval tilt makes confidence finally affect ranking — previously it was nearly inert (pure cosine). **Honesty/limits:** the outdated signal is a *probable* fix, not proof (an unrelated edit in the same hunk also outdates a comment), so a confirm is `fixed` not certainty — but it only ever *adds* a confirm, never silences a finding, and the Wilson lower bound discounts thin evidence, so the false-positive blast radius is bounded. Analyzed pitfalls aren't linked by `pitfallId` (created pre-cluster), so consolidation rarely revisits them — their *initial* `confidenceFromOutcomes` is the main story, which is exactly why fixing it (not the consolidation math) was the leverage. **Quality floors:** `retrieval-quality` (recall 7/8) and `ranking-quality` (nDCG 0.9) stay green — corpora use uniform confidence so the new tilt scales without reordering. **Frozen test contract updated deliberately** (the old `outcome.test.ts` pinned the binary mapping precisely so a change here would be test-breaking). Deferred to the hosted/team path (unchanged from the design note): GraphQL `isResolved` corroboration and revert detection — both need the API + rate-limit discipline and stay out of the local-first path.

## ADR-45 — Optional persistent local visualization daemon (`plex serve`) 🧪 (provisional)
**Context.** Users want to *see* their data — click a node, expand its neighbors, browse the code graph, the PR brain, and the knowledge base. That visceral graph UI is the one thing FalkorDB gave for free (its bundled Browser) and the reason it was first chosen; ADR-30/33 then deleted FalkorDB **and** Kùzu Explorer to honor the embedded, "nothing-running, no-Docker" pitch. The static `plex review --html` (M5 viz, `engine/viz.ts`) shows only one review's neighborhood — a snapshot, no clicking-in, no brain/knowledge view. The MCP server can't host a URL: it's a **stdio** transport that idle-drops after seconds and re-spawns per call (per the server `instructions`) — there's no port, and it's spawned per-client. claude-mem's always-on UI comes from a **separate persistent daemon**, not its MCP transport.
**Decision.** Add **one optional, local-only, Plex-owned node daemon** — `plex serve` — that serves an interactive Cytoscape UI at `http://127.0.0.1:2288` (port configurable via `PLEX_UI_PORT`, auto-fallback if taken) over a JSON API reading the three existing stores (Kùzu code graph, Kùzu brain, JSON knowledge). This **narrows, not reverses, the embedded principle**: *no Docker and no external/native services* still holds — the daemon is the **same node runtime** Plex already ships, npm-distributed (`npx -y -p @sshanzel/plex@<pin> plex serve`, mirroring the `plex-mcp` launch), with **zero new runtime deps** (node's built-in `http`, no framework). New package `@plex/viz-server`; CLI gains `serve [--stop|--status|--foreground|--port]` (idempotent detached spawn + pidfile `~/.plex/daemon.json`). **One daemon serves every repo on the machine** (storage is machine-global at `~/.plex/repos/<id>`) via a repo picker. **Auto-start is universal and on by default — driven by the MCP server itself**, not a client-specific hook: on startup `plex-mcp` best-effort spawns the daemon (`ensureDaemon`: probe first → detached-spawn its sibling `plex.js serve --foreground` only when down). This covers *every* client — Claude plugin, Codex plugin, or a bare MCP registration — with **no CLI install** (the daemon ships in the same npm package the MCP already runs from) and no client-specific file. It's **stdout-safe** (writes nothing to the stdio protocol channel, swallows errors) and opt-out via `PLEX_NO_UI=1`. A `SessionStart`-hook approach was **considered and rejected**: it fires only for Claude Code (Codex + bare-MCP users would silently miss the UI) and races the MCP path. Manual escape hatch for CLI-only users: `npx -p @sshanzel/plex plex serve`.
**The Kùzu single-writer constraint is the load-bearing design point.** A long-lived daemon must **never hold a Kùzu handle**: it would take the single-writer lock and make a concurrent review's open throw `RepoBusyError` — i.e. *the viewer could break reviews*, and vice-versa. So the daemon **opens per-request, queries, and closes immediately**, and translates `RepoBusyError` into a `503` the UI shows as "repo busy — retrying". Read-only opens (which would allow shared readers) are **not** an option: Kùzu 0.11.3's read-only open SIGSEGVs on Linux (ADR-40). Collisions are brief (a review opens the graph only for the neighborhood walk) and transient; the cost is an occasional retry, accepted.
**Security.** Bind **127.0.0.1 only** (never `0.0.0.0`) → no remote exposure, so no auth. Repo ids from the request are **validated against the enumerated registry** (dirs under the repos root) and rejected unless `^[A-Za-z0-9._-]+$` AND present in that set — no path-traversal into arbitrary dirs (consistent with the PR-13 containment posture). All data is rendered escaped (no `innerHTML` of store text). The UI is read-only — it never writes a verdict or mutates a store.
**Consequences.** The FalkorDB-UI need is met by a viewer over the stores you already own — no database engine reintroduced, no Docker, no native service, no cross-engine SIGSEGV. Marked **provisional (🧪)**: it's the first long-lived local process Plex ships, so the no-services line is now "no *external/Docker* services; one optional local node daemon." Limitations (accepted for v1): only **centralized** repos appear (an in-repo `PLEX_DATA_DIR=.plex` opt-in or a linked-worktree `.plex` has no central registry — documented); the daemon is **per-machine**; and a busy repo (mid-review) shows a transient retry. Distribution rides the existing lockstep pin (the daemon ships in the same npm package; the plugin hook pins the same engine version). Builds toward `docs/milestones/M13.md`.
